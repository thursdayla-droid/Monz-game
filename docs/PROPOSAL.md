## 1. MONZのコンセプトの理解

MONZは「**世界に1体だけの相棒が、自分の育て方によって“その子らしく”なっていく様子を見守るゲーム**」だと理解しています。

- 主役は「強さ」ではなく「**愛着**」。バトルも育成も、相棒の個性を見せる場として機能する。
- 個性は3層でできている：
  1. **生まれ持ったもの**（DNA：見た目・素質・隠れた性格）
  2. **育ち**（お世話・ミニゲーム・経験で少しずつ変わる性格と能力）
  3. **その瞬間の気分**（感情：喜び・怒り・眠気など）
- プレイヤーは言葉ではなく、**動き・表情・鳴き声**から相棒の気持ちを読み取る。
- バトルは完全オートなので、「**自分が育てた結果がそのまま戦い方に出る**」ことが面白さの核になる。慎重な子は様子を見て、負けず嫌いな子は劣勢でも突っ込む。
- 絵柄はアメリカンカートゥーン×UKポップパンク。可愛いだけでなく、不格好・生意気・間抜けも魅力。BUNKは「方向性の参考」であって「型」ではない。既存作品（特にポケモン）に似せないことが最重要。

## 2. iPhoneだけで開発するための推奨構成【提案】

### 技術構成

| 用途 | 推奨 | 理由 |
|---|---|---|
| ゲームエンジン | **Phaser（最新安定版）＋ TypeScript** | 2Dに強い・Safariで動く・資料が多い。将来 Capacitor でiOS/Androidアプリ化しやすい |
| ビルド | **Vite** | 速い・設定が少ない |
| ロジックのテスト | **Vitest** | DNA生成・性格計算・バトル判断を自動テスト |
| 画面の自動確認 | **Playwright（iPhoneサイズで撮影）** | PCがなくても、GitHub上でスクリーンショットを確認できる |
| 公開・確認 | **GitHub Pages**（GitHub Actionsで自動公開） | 無料。iPhoneのSafariでURLを開くだけで遊べる |
| 保存 | 最初は端末内（IndexedDB）＋ バックアップ書き出し | サーバー不要で始められる |
| サーバー | Supabase（オンライン要素が必要になった段階で） | 指示書どおり後回し |
| アプリ化 | Capacitor（後続フェーズ） | Webのコードをほぼそのまま使える |

### iPhoneからの開発の流れ

```
企画者（iPhone）
  │ ① Claude Code（claude.ai/code・Claudeアプリ）に依頼
  ▼
Claude Code（クラウド）がコードを書き、ブランチにpush → Pull Request作成
  │ ② GitHub Actions が自動で：テスト／iPhoneサイズのスクショ撮影／プレビュー公開
  ▼
企画者（iPhone）
  │ ③ PRのスクショを見る・SafariでプレビューURLを開いて実際に遊ぶ
  │ ④ ChatGPTにPRをレビューしてもらう（任意）
  ▼
⑤ GitHubアプリでPRを「Merge」 → 本番URLが自動更新
```

- **パソコンは一度も使いません。** コマンド操作は全てClaude CodeとGitHub Actionsが行います。
- iPhoneのSafariには開発者ツールがないため、URLに `?debug=1` を付けると**画面上にログやステータスを表示するデバッグ表示**を出せるようにします。
- 「ホーム画面に追加」すると全画面のアプリのように遊べます（PWA）。

### リポジトリについて【要判断】

【確定】MONZ専用の公開リポジトリ `monz` で開発します。

推奨フォルダ構成（新リポジトリ）：

```
monz/
├─ src/
│  ├─ core/        … ゲームのルール（画面に依存しない純粋なロジック）
│  │  ├─ dna/          DNA生成・外見パラメータ
│  │  ├─ personality/  性格・感情
│  │  ├─ stats/        ステータス・成長
│  │  ├─ behavior/     行動の意思決定（ホームとバトルで共用）
│  │  ├─ battle/       バトルシミュレーション
│  │  └─ minigame/     ミニゲームの差し込み口（中身なし）
│  ├─ render/      … MONZの描画とアニメーション
│  ├─ scenes/      … タイトル・誕生・ホーム・バトルの各画面
│  ├─ save/        … 保存・読込・データ移行
│  └─ data/        … 質問・パレット・パーツ定義（企画者が編集しやすい形式）
├─ tests/
├─ docs/           … 仕様書・決定事項の記録
└─ .github/workflows/  … 自動テスト・自動公開
```

「ルール（core）」と「見た目（render）」を分けることで、将来オンライン対戦でサーバー側に同じルールを置いたり、アプリ化したりしやすくなります。

## 3. 個体ごとに違う外見を作り、動かす技術案【提案】

### 基本方針：「DNA → 体の設計図 → コードで描いて、コードで動かす」

画像を1枚ずつ作るのではなく、**DNA（数値の集まり）から体を組み立て、ベクター（線と面）でその場で描く**方式を提案します。

```
回答（5問） ─┐
ランダム種  ─┼→ DNA ──→ 体の設計図 ──→ 描画（太い輪郭線つき）
隠れた個性  ─┘   │                       │
                 └→ 性格・素質             └→ 骨組み（リグ）で動かす
```

### 3-1. 体の設計図（シルエットに個体差を出す）

単純な色違いにならないよう、**3段階**で差を作ります。

1. **体型タイプ（大きな骨格の違い）** — 例：
   - ずんぐり拳タイプ（BUNKのような、腕と拳が大きく体が低い）
   - 頭でっかちタイプ
   - 細長・ひょろひょろタイプ
   - まんまる・ぷよぷよタイプ
   - 四つ足タイプ
   - 浮遊タイプ（足がない）
   ※具体的な体型の種類は、デザイン担当（企画者・ChatGPT）と一緒に決めます。
2. **プロポーション（連続的な数値）** — 頭の大きさ、胴の太さ、手足の長さ、拳の大きさ、猫背度合い、左右非対称度など。数値なので無限に近いバリエーションになります。
3. **パーツ（差し替え＋変形）** — 目・口・角/トサカ/耳・腕先・足・しっぽ・背中の飾り。各パーツは数種類の形 × 大きさ・角度・曲がり具合の数値で変化。

さらに**色（キュレーション済みの配色セットから選ぶ）**と**模様（しま・ぶち・チェッカー・つぎはぎ等）**を重ねます。配色は完全ランダムにすると汚くなるため、パンク／ポップな**配色セットをあらかじめ用意**し、その中で揺らぎを持たせます。

### 3-2. 描画方式

- 体の輪郭は「ベジェ曲線・スーパー楕円」などの数式で作るため、プロポーションの数値を変えるとシルエットそのものが滑らかに変わります。
- 輪郭は太い線、塗りはフラット＋影1段（カートゥーン調）。
- 最初は**コードで描いた仮の形**で始め、後からデザイナーが描いた**SVGパーツに差し替えられる**作りにします（パーツごとに「つなぎ目の位置」を決めた規格を用意）。

### 3-3. 動かし方（自然なアニメーション）

パーツの組み合わせが無数にあるため、1体ずつ手作りのアニメーションは作れません。そこで**骨組み（リグ）＋プログラムによるアニメーション**にします。

| 動き | 方法 |
|---|---|
| 呼吸・待機 | 体を少し伸び縮み（スクワッシュ＆ストレッチ） |
| 歩く・走る | 足の位置を計算して動かす（簡易IK）。体型ごとに歩き方を変える（ぴょこぴょこ、どすどす、ふわふわ） |
| 耳・しっぽ・角の揺れ | ばねの物理計算で遅れてついてくる（二次モーション） |
| 表情 | 目と口の形を数値で変形（喜び＝目が細くなる、怒り＝眉が下がる 等）、まばたき |
| 感情の身振り | 喜びのジャンプ、怒りの地団駄、眠気でこっくり 等を「動きの部品」として用意し、性格で強さ・速さを変える |
| 鳴き声 | 数種類の音源を、個体ごとに高さ・速さ・揺れを変えて再生（Web Audio） |

### 3-4. なぜ生成AI画像やSpineを使わないか

| 方式 | 問題点 |
|---|---|
| 生成AIで毎回画像生成 | コマごとに絵がブレて**アニメーションにできない**／費用がかかる／既存作品に似る危険を管理しにくい |
| Spine / DragonBones | 良いツールだが**PCでの作業が前提**。パーツの組み合わせが多いと1体ずつ作る必要がある |
| 本提案（コード描画＋プログラムアニメ） | 絵の質はデザイン規格で担保する必要がある。代わりにiPhoneだけで完結し、組み合わせ無限・データが軽い |

生成AIは「パーツやデザイン案のアイデア出し」に使うのは有効です（最終素材は人が確認）。

### 3-5. 固有IDと「見た目の重複」対策

- **固有ID**：誕生時に重複しないID（ULID等）を発行。これは簡単です。
- **見た目の重複**は別問題です。対策：
  1. 外見を数値の並び（**外見指紋**）に変換し、「見た目の距離」を計算できるようにする。
  2. 誕生時、既存の個体と**距離が近すぎたら、隠れたランダム要素を振り直す**。
  3. 端末内では自分の個体同士で判定。**全プレイヤー間での重複判定にはサーバー（Supabase）が必要**なので、オンライン導入時に対応します。
- **重要**：DNAに「生成ルールのバージョン」を記録します。後でパーツを追加・調整しても、**既に生まれた子の見た目が勝手に変わらない**ようにするためです。

### 3-6. DNAと質問の関係

- 質問の回答は「傾向（例：好奇心↑、拳が大きくなりやすい、暖色寄り）」を与えるだけで、結果を決めません。
- 影響度の比率（40:60案）は設定ファイルの数値にし、企画者が後から調整できるようにします。
- 同じ回答でも、ランダム種と隠れた個性で必ず違う子が生まれます。

## 4. 性格・行動・バトルの仕組み【提案】

- **性格**：隠しパラメータ（勇敢さ・慎重さ・好奇心など）を0〜100の数値で保持。経験でゆっくり変化。
- **感情**：短期的な状態。出来事で上がり、時間で落ち着く。性格によって上がりやすさが違う（なでられて喜ぶ子／嫌がる子）。
- **行動の決め方（ユーティリティAI）**：ホームでもバトルでも、「今とれる行動」それぞれに点数をつけ、高いものを（少しランダムに）選びます。
  - 点数 ＝ 状況（体力・距離・空腹など）× 性格の重み × 今の感情 × 過去の経験
  - ホームの「寝る・遊ぶ・ちょっかいを出す」と、バトルの「攻める・守る・下がる・技を使う」を**同じ仕組み**で扱うため、「性格が普段の行動と戦い方の両方に出る」が自然に実現します。
  - 将来、点数のつけ方を機械学習モデルに差し替えられる設計にします。
- **バトル**：一定間隔で進む**決定的シミュレーション**（同じ乱数の種なら必ず同じ結果）にします。リプレイ保存・戦闘履歴・将来のオンライン対戦での不正防止に必要です。
- **ミニゲーム**：「ミニゲームを登録する口」と「結果を育成に反映する口」だけを用意し、**ミニゲーム自体は作りません**。

## 5. 最初の試作品で実装すべき範囲【提案】

いきなりPhase 2の全部を作るより、**一番難しく、一番大事な「外見の個体差と動き」を先に確かめる**ことを推奨します。

### 試作0：Phase 1（準備）＋「MONZ生成テスト画面」

- 新リポジトリの土台（Phaser＋TypeScript＋Vite）、自動テスト、GitHub Pagesへの自動公開
- **生成テスト画面**：ボタンを押すとランダムなDNAからMONZが生まれ、画面上で呼吸・まばたき・歩く。12体などを一覧表示して、**個体差が十分か・可愛い/格好いい/変か・既存作品に似ていないか**を企画者がiPhoneで確認できる
- 仮の体型タイプ2〜3種、仮のパーツ各2〜3種、仮の配色数セット
- `?debug=1` のデバッグ表示

→ ここで企画者・ChatGPTに見た目の方向性を判断してもらってから、Phase 2に進みます。

### その後の試作1：Phase 2（誕生システム）

- タイトル → 仮の質問5問（**文面は仮。正式な質問は企画者が決める**） → 誕生演出 → 名前入力 → 保存
- 再訪時に同じ子が表示される

### 試作でやらないこと

ミニゲーム、街、進化、オンライン、課金、部屋の家具カスタマイズ。

## 6. 技術的な難所と解決策

| 難所 | 内容 | 解決策 |
|---|---|---|
| 個体差と絵の質の両立 | 組み合わせ式は「安っぽく」「バラバラ」になりがち | 数値の範囲と組み合わせ制限をデザイン規格として決める。一覧画面で大量に見比べて調整。後で手描きSVGパーツへ差し替え |
| 既存作品に似ない保証 | 自動では判定できない | 一覧画面で人が確認する工程を必ず入れる。既知の特徴的モチーフ（特定の耳型・ほほの丸・尻尾の形など）を禁止リストにする |
| 自然な動き | パーツが無数にあると手作りアニメ不可 | 骨組み＋プログラムアニメ＋ばね物理。動きの部品を体型ごとに調整 |
| iPhone Safariのデータ消失 | Safariは**7日間サイトを開かないと保存データを消す**ことがある | 「ホーム画面に追加」で遊ぶことを推奨＋バックアップの書き出し/読み込み機能。本格的にはSupabaseでのクラウド保存 |
| iPhoneでデバッグできない | Safariに開発者ツールがない | 画面上のデバッグ表示、自動スクショ、ロジックの自動テスト |
| 音が鳴らない | iOSは最初のタップまで音を出せない | タイトル画面の「タップしてスタート」で音を有効化 |
| オートバトルのバランス | 性格の強弱で一方的になる | シミュレーションを大量に自動実行して勝率を集計するテストを用意 |
| 保存データの互換性 | 更新で古いデータが壊れる | 保存データにバージョン番号を持たせ、移行処理を用意 |
| 将来のオンライン不正 | 端末側の数値は改ざんできる | バトルを決定的シミュレーションにしておき、後でサーバー側で同じ計算を検証 |

### 受け取った資料
1. 誕生シミュレーション例（BUNK／MOFU／ZIPP／PUNI／KLAK、質問5問と回答、ステータス例）

### 設計への反映【提案】
- **外見方式の修正**：参考の5体は、毛並み・キノコ・機械パーツなどの描き込みが多く、シルエットも大きく違います。コードの図形だけでこの品質を出すのは難しいです。そこで次の**混合方式**に変更します。
  - **系統（ファミリー）**：BUNK系・MOFU系のように系統ごとに、パーツに分けた絵（胴・頭・腕・足・しっぽ・顔パーツ）を用意する
  - **個体差**：系統の中で、プロポーションの変形（メッシュ変形）・パーツの差し替え・配色の置き換え・模様・表情で差をつける
  - **動き**：パーツを骨組みにつないで、プログラムで動かす（3章の案はそのまま）
- **試作0**：BUNK系1系統だけで、パーツ分けした絵を骨組みで動かし、変形と配色で個体差を出して、品質を確かめる。
- **質問**：参考資料の5問を「仮の初期質問」として使う。
- **ステータス**：参考資料に合わせて、初期値はおよそ30〜90の幅を目安にする（未確定）。

### 確認が必要な点
- **既存作品との類似リスク**：
  - ZIPPの「黄色い体＋先が黒い長い耳」は、ピカチュウを連想させる組み合わせです。
  - PUNIの「背中にキノコ」は、パラス／パラセクトを連想させる可能性があります。

### 腕を下ろした姿・表情・動きの追加（2026-10-19 企画者承認・【仮】テスト実装）
