# MONZ 分岐進化システム 仕様書

- 2026-10-20：企画者から共有された仕様を記録した。
- **これは記録だけ。まだ作らない。** 進化の仕組みのプログラム、今あるゲームの変更、進化した姿の絵づくりは、企画者の許可が出るまで行わない。
- 【確定】は企画者が決めたこと、【未確定】はこれから決めること、【提案】は Claude Code からの案（まだ決まっていない）。

## 1. 基本の考え方【確定】

- 育て方によって、進化した姿が変わる（分岐進化）。
- 同じ種類の MONZ でも、プレイヤーによって違う姿に進化することがある。
- 進化先はプレイヤーが選ばない。それまでの育て方から自動で決まる。
- プレイヤーごとの育成の歴史が、MONZ の姿に出ることを大事にする。

## 2. 進化の回数とレベル【確定】

| 形 | 進化した回数 | 進化できるレベル |
|---|---|---|
| 初期形態 | 0回 | ― |
| 第2形態 | 1回 | Lv.30 |
| 最終形態 | 2回 | Lv.60 |

- 進化は最大2回。最大レベルは Lv.100。
- 進化してもレベルは戻らない（Lv.30 で進化したら、進化後も Lv.30）。

## 3. ステータスの引き継ぎ【確定】

- 進化前に育てたステータスは、そのまま引き継ぐ。
- ステータスは6種類：HP・パワー・タフネス・スピード・テクニック・愛。
- 進化でレベルやステータスが初期化されることはない。
- 【未確定】進化したときにステータスのボーナスを足すかどうか。
- 【確定】能力が大きくなりすぎない（インフレしない）設計にする。

## 4. 育て方による分岐【確定は方向性だけ】

- 育て方の傾向で進化先が変わる。例：パワー重視 → 力強い形、スピード重視 → 俊敏な形、タフネス重視 → 守りの形、テクニック重視 → 技巧的な形。
- 上の例は方向性の説明。【未確定】具体的な進化形態、分かれる数、判定の条件。
- 【確定】種族ごとの伸びやすさの違いを考える。「いちばん高いステータス」だけで決めない。
  - 理由：BUNK のように、もともとパワー・タフネスが伸びやすい種族は、何もしなくてもその能力がいちばん高くなるため。

## 5. 進化先は選べない【確定・重要】

- プレイヤーは進化先を直接選べない。システムが自動で決める。
- 候補をいくつか見せて選ばせる機能は作らない。
- 【未確定】進化先を決める計算式。

## 6. 進化の演出【確定は方針だけ】

- 進化する瞬間まで、新しい姿は分からない。
- 「パワー型に進化します」などの予告は出さない。
- 進化した時に、新しい姿を初めて見せる。
- 【未確定】アニメーション・エフェクトの中身。

## 7. 進化前の姿には戻れない【確定】

- 一度進化した MONZ は、前の姿に戻れない。前の姿に切りかえる機能も作らない。
- 進化は特別な成長のイベントとして扱う。

## 8. 愛【確定】

- 愛は MONZ だけの特別なステータス。
- レベルアップの自由ポイントは振り分けられない。毎日のごはん・なでるなどのお世話で育つ。
- 愛が高いほど、次の確率が上がる：
  - CPU オートバトル：やられる攻撃を1回だけ耐える
  - 冒険ダンジョン：戦闘不能になっても1回だけ復活する
- 【未確定】愛が進化先に関係するかどうか。
- 【確定】愛による隠し進化などを勝手に足さない。

## 9. 今の成長の仕組みとの関係

### 今のプログラムの仕組み（2026-10-20 時点）

- 通常ステータス5種と愛：`src/core/stats.ts`。セーブデータ：`src/core/lifeSave.ts`。
- レベルが1上がるごと：
  - 自動成長が合計3。種族ごとの入りやすさに合わせて、ランダムに入る。BUNK は HP6・パワー9・タフネス8・スピード3・テクニック4 の割合。
  - 自由ポイントが1。好きな通常ステータスに1ずつ振る。愛には振れない。振り直しはできない。
- 保存しているもの：自動成長の合計（`auto`）と、自分で振った合計（`alloc`）を別々に保存している。今のステータス ＝ 種族の初期値 ＋ auto ＋ alloc。
- 通常ステータスの上限は150。愛は初期20・最大100。
- 次のレベルまでの経験値：110 ＋（レベル − 1）× 15。
  - Lv.30 までに合計 9,280。Lv.60 までに 32,155。Lv.100 までに 83,655。

### 合わないところ（企画者に確認したいこと）

1. **成長の数字**：今回の仕様書は「自動成長 合計3.0・自由ポイント 0.1」。でも、2026-10-20 に企画者の指示で「小数をやめて、自動ランダム3・自由ポイント1」に変えていて、プログラムもそうなっている。**今の整数の仕組みのままでよいか。**
2. **最大レベル Lv.100**：今のプログラムにはレベルの上限がない。進化を作るときに Lv.100 で止める処理を入れる。
3. **今ある「進化の4段階（BABY/KID/TEEN/FINAL）【未確定】」の記録**（PROPOSAL.md）：今回の「進化は最大2回（3つの形）」に置きかえる。
4. **Lv.100 のときのステータスの合計**：BUNK だと、初期値35 ＋ 自動297 ＋ 自由99 ＝ 431（5種の合計）。1つの能力の上限150には収まる。インフレの目安として記録しておく。
5. **進化までの時間**：お世話だけ（1日50経験値まで）だと、Lv.30 まで約186日かかる。ミニゲームの経験値を足して、どのくらいで進化させたいかは【未確定】。VISION.md の「よく遊ぶ人で約2日に1レベル」なら、Lv.30 で約2か月、Lv.60 で約4か月。

### 判定で気をつけること【確定】

- プレイヤー自身の育て方が、ちゃんと進化先に出るようにする。
- 判定の式はまだ作らない。

## 10. ゲームバランス【確定】

- 進化は最大2回、最大 Lv.100。レベルが戻らないので、何度もくり返して強くなる仕組みにはしない。
- 育てた成果は感じられるようにする。ただし能力が大きくなりすぎないようにする。
- オンライン対戦・MOBA では、育てたステータスをそろえて（標準化して）公平にする方針。今のプログラムにも、モードごとに強さを変える入り口（`statsForMode`）だけある。

## 11. キャラクターデザイン【確定】

- 進化した姿は、すべて完全オリジナル。既存のモンスター育成ゲームのキャラクターをまねしない。
- MONZ の世界観：アメリカンカートゥーン、ストリート、ポップで個性的。
- 進化した姿の絵は企画者が作って渡す。Claude Code は進化後のデザインを勝手に決めない（絵を作らない）。
- 絵の扱いは、今の MONZ と同じ（企画者の絵を切り抜いて使う。描き直さない）。

## 13. 作るときのデータの形【提案】

まだ作らない。作るときの案として残す。

### 13-1. セーブデータ（1匹ぶん `MonzData` に足す）

```ts
interface MonzData {
  // …今あるもの…
  /** 進化の記録(進化していなければ stage 0・history は空) */
  evolution: {
    /** 0 初期形態 / 1 第2形態 / 2 最終形態 */
    stage: 0 | 1 | 2;
    /** 今の形の番号(種族の進化表の番号。初期形態は 'base') */
    form: string;
    /** 進化した記録(戻せない。あとで見返す・確認するため) */
    history: {
      stage: 1 | 2;
      form: string;
      level: number;
      at: number; // 進化した時刻
      /** 進化を決めたときの元データ(式が変わっても、なぜこの形になったかを残す) */
      snapshot: { auto: StatBlock; alloc: StatBlock; love: number; careCount: { feed: number; pet: number } };
    }[];
  };
}
```

- セーブデータの版を1つ上げる（今は版4 → 版5）。古いデータは `{ stage: 0, form: 'base', history: [] }` を入れるだけ（1回だけ・何度やっても同じ結果）。既存のデータは消さない。
- `auto`（自動成長）と `alloc`（自分で振った分）は、もう別々に保存している。進化の判定で「プレイヤー自身の育て方」を見るのに、そのまま使える。

### 13-2. 種族ごとの進化表（プログラムの中の表）

```ts
/** 種族ごとの進化先。形の中身(名前・絵・判定のための向き)は企画者が決めたら入れる */
const EVOLUTION_TREE: Record<SpeciesId, {
  stage1: EvolutionForm[]; // 第2形態の候補
  stage2: Record<string, EvolutionForm[]>; // 第2形態ごとの、最終形態の候補
}>;

interface EvolutionForm {
  id: string;
  /** 判定に使う向き(例: パワー寄り・スピード寄り…)。式が決まってから中身を決める */
  tendency: Partial<Record<StatKey, number>>;
  /** 見た目の絵(企画者の絵) */
  art: string;
}
```

- 候補はプレイヤーに見せない（選ばせないため）。

### 13-3. 判定の入り口（中身は空のまま）

```ts
/** 進化先を決める。式が決まるまで中身は作らない。乱数を使うなら MONZ の番号から作る(同じなら同じ結果) */
function decideEvolution(monz: MonzData, stage: 1 | 2): string;
```

- 「いちばん高い能力」だけで決めないため、たとえば次のような材料が使える【提案・未決定】：
  - 自分で振ったポイント（`alloc`）の割合：プレイヤーの方針がいちばん出る
  - 自動成長（`auto`）を、種族の伸びやすさで割った値：種族の得意をならしたもの
- 判定の部品は Phaser を使わない場所（`src/core/`）に置く。テストで、同じ育て方なら同じ結果になることを確かめる。

### 13-4. 見た目

- 進化した形ごとに、企画者の絵（切り抜き）を使う。今の BUNK と同じ扱い。
- DNA で見た目を決める部分を変えるときは `GENERATOR_VERSION` を上げて、今いる MONZ の見た目が変わらないようにする（CLAUDE.md のルール）。

### 13-5. 気をつけること

- 進化しても、今のステータス（初期値 ＋ auto ＋ alloc）が変わらないようにする。形ごとに「初期値」を変えると数字が変わってしまうので、ボーナスを入れるなら別に `evolutionBonus` として足す（入れるかは未確定）。
- 今のプログラムは、古いセーブデータを直すとき、自動成長をレベルから計算し直している（`autoGrowthAt`）。進化後に伸びやすさを変える場合は、計算し直さずに保存した値を使う形にする。
